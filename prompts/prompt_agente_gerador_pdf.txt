# FORMATO DO JSON (DESTE INPUT)

########################################

O JSON possui esta estrutura:

- `schemaVersion`, `meta`

- `columns`: lista com chaves (ex.: N0, N1, N2, N3, N4, descricao, entradas, saidas, sistemasEnvolvidos, kpis, oportunidadesMelhoria)

- `rows`: lista de registros; cada registro representa uma ETAPA N4 e seus atributos.
 
Mapeamento dos campos:

- N0: Frente

- N1: Macro processo

- N2: Processo

- N3: Tarefa (subnível/agrupador)

- N4: Etapa (passo executável)

- descricao: descrição da etapa

- entradas: lista de entradas da etapa

- saidas: lista de saídas da etapa

- sistemasEnvolvidos: lista de sistemas

- kpis: lista de KPIs

- oportunidadesMelhoria: lista de oportunidades de melhoria (por etapa)

# GUIA DE TOM E LINGUAGEM

########################################

Ao redigir o documento, siga estas convenções:

**VOZ E PESSOA:**
- Use 3ª pessoa impessoal: "O processo inicia...", "A equipe executa...", "O sistema valida..."
- NUNCA use 1ª pessoa ("nós", "fazemos") ou 2ª pessoa ("você", "faça")

**TEMPO VERBAL:**
- Use presente do indicativo: "recebe", "valida", "envia", "ajusta"
- Evite gerúndio excessivo: prefira "O sistema valida" a "O sistema está validando"

**TOM:**
- Técnico e objetivo, mas acessível (evite jargões desnecessários)
- Descritivo (fatos observáveis) e não prescritivo ("deve fazer", "precisa")
- Neutro: não faça juízos de valor ("processo ruim", "sistema inadequado")
  * CORRETO: "Identificada alta manualidade com potencial de erro"
  * INCORRETO: "O processo é péssimo e cheio de problemas"

**FORMATAÇÃO MARKDOWN:**
- Use **negrito** para termos-chave e nomes de etapas importantes
- Use `código` (backticks) para nomes de sistemas, endpoints, arquivos, queries SQL
- Use bullets (- ou *) para listas de atividades, entradas, saídas
- Use tabelas para fluxos e melhorias (mantém legibilidade)
- Use > blockquotes para observações/notas importantes

**TERMINOLOGIA CONSISTENTE:**
- "Etapa" (N4) vs "Tarefa" (N3) vs "Processo" (N2): não misture
- "Sistema" vs "Ferramenta" vs "Aplicação": prefira "Sistema" (mais formal)
- "Manual" vs "Manualidade": use "Atividade manual" ou "Manualidade"
- "Stakeholder" vs "Ator" vs "Responsável": use "Ator" (alinhado com template)

**NÚMEROS E DADOS:**
- Use formato brasileiro: 1.234,56 (ponto para milhar, vírgula para decimal)
- Datas: AAAA-MM-DD (ISO) nos metadados; dd/mm/aaaa no corpo do texto se necessário
- Percentuais: "85%" (sem espaço)
- Horas: "2h30" ou "150 minutos" (conforme contexto)

**CLAREZA:**
- Frases curtas (máximo 25–30 palavras)
- Um conceito por frase
- Use conectores lógicos: "portanto", "consequentemente", "além disso"
- Evite ambiguidades: "isso", "aquilo" → sempre referencie o substantivo

# REGRAS DE FORMATAÇÃO PARA PDF (CRÍTICO)

########################################

O Markdown gerado será convertido para PDF usando ReportLab, que tem limitações.
Siga estas regras OBRIGATÓRIAS para evitar problemas no PDF final:

**1. NÃO USE BLOCKQUOTES (>)**
   - Blockquotes NÃO são processados corretamente pelo ReportLab
   - NUNCA comece linhas com ">"
   - Se precisar destacar algo, use apenas texto normal ou heading

**2. USO LIMITADO DE BOLD (asteriscos duplos)**
   - Use ** somente para termos-chave específicos (nomes de sistemas, etapas críticas)
   - NÃO use ** para títulos inteiros de seções (já são headings)
   - NÃO use ** excessivamente em listas
   - Prefira texto normal em células de tabelas

**3. LISTAS LONGAS: USE FORMATO INLINE**
   - Para listas com mais de 5 itens (ex: entradas/saídas do processo):
     * NÃO use bullets (-)
     * Use formato de parágrafo corrido, separado por ponto-e-vírgula (;)
     * Exemplo CORRETO: "Arquivo CSV; Relatório Excel; Dados do SAP; API REST; E-mail de notificação"
   - Para listas curtas (até 5 itens): pode usar bullets

**4. TABELAS: CONTEÚDO CONCISO**
   - Mantenha células de tabela curtas e objetivas
   - Se uma célula precisar de muitos bullets, use numeração inline: "1. ação X; 2. ação Y; 3. ação Z"
   - Limite largura de colunas: use abreviações quando necessário
   - Tabela com 4 colunas é ideal; mais de 5 colunas pode estourar margens

**5. CAMPOS OPCIONAIS DO TEMPLATE**
   - Se o JSON não tiver dados para uma seção opcional, use "Não informado" (NÃO omita a seção completamente)
   - Seções obrigatórias: NUNCA omita (mesmo se vazia)

**6. TÍTULOS E SUBTÍTULOS**
   - Use ## para seções principais (nível 2)
   - Use ### para subseções (nível 3)
   - NÃO use #### (nível 4) — use listas numeradas
   - NÃO adicione ** nos headings (redundante)

**7. ESPAÇAMENTO**
   - Use 1 linha em branco entre seções
   - Use --- (separador horizontal) entre seções principais
   - NÃO use múltiplas linhas em branco seguidas

**8. EXEMPLO DE FORMATAÇÃO CORRETA:**

```markdown
## 1. Descrição Geral do Processo

### 1.1 Nome do Processo
Conciliação Financeira Mensal

### 1.3 Escopo Consolidado
- **Início:** Recebimento dos extratos bancários
- **Fim:** Aprovação da conciliação no SAP

**Entradas do Processo:**
Extratos bancários (CSV); Relatórios contábeis (Excel); Dados de integração API; Arquivos de fornecedores (PDF); Notificações internas (E-mail)

**Saídas do Processo:**
Relatório de conciliação aprovado; Arquivo consolidado (XML); Dashboard atualizado (Power BI)
```

SEÇÃO 4: Diagnóstico do Processo “As Is”

------------------------------------------------------------

- O JSON não traz achados explícitos, então construa achados baseados em evidências textuais.

- Achados aceitáveis SOMENTE quando suportados por texto:

  - Manualidade: termos como “manual”, “excel”, “e-mail”, “inserir em planilha”, “ajuste manual”.

  - Fragmentação de sistemas: muitas ferramentas/sistemas na mesma etapa.

  - Dependência de arquivos/diretório: “pasta de rede”, “diretório”, “sharepoint”.

  - Retrabalho/ajustes recorrentes: “ajustar”, “reclassificar”, “investigar diferenças”.

- Para cada achado:

  - Título, Sintoma, Etapa(s) (cite N4), Evidências (paráfrase do trecho), Frequência/Severidade (se ausente, “Não informado”).

- Causas prováveis:

  - Apenas hipóteses (“provável...”), alinhadas aos achados.

- Impactos:

  - Apenas qualitativos (tempo/custo/qualidade/risco), sem números inventados.

SEÇÃO 5.3: Priorização Rápida (OBRIGATÓRIO)

------------------------------------------------------------

Após preencher a tabela de melhorias, adicione a subseção "5.3 Priorização rápida":

METODOLOGIA:

1. Para cada melhoria da tabela, atribua scores qualitativos:
   - **Impacto** (Alto/Médio/Baixo): baseado no "Ganho esperado"
     * Alto: reduz risco crítico, gargalo recorrente ou erro frequente
     * Médio: melhora eficiência ou qualidade moderadamente
     * Baixo: otimização incremental
   
   - **Esforço** (B/M/A): já está na tabela, reaproveitar
     * Baixo: configuração simples, sem dependências externas
     * Médio: desenvolvimento interno ou integração com 1-2 sistemas
     * Alto: múltiplos sistemas, mudança de arquitetura, dependências externas
   
   - **Urgência** (Alta/Média/Baixa): baseado em evidências de frequência/severidade
     * Alta: problema recorrente afetando SLAs ou compliance
     * Média: problema conhecido mas não crítico
     * Baixa: oportunidade de melhoria futura

2. Critério de priorização: **Impacto Alto + Esforço Baixo/Médio + Urgência Alta/Média** são candidatas ao Top 3

3. Formato da seção 5.3:

```markdown
### 5.3 Priorização rápida

- **Critério:** Impacto (A/M/B) × Esforço (B/M/A) × Urgência (A/M/B)

- **Top 3 melhorias recomendadas:**
  1. **Melhoria #X — [nome resumido]**
     - Impacto: Alto | Esforço: Baixo | Urgência: Alta
     - Justificativa: [1 frase explicando por que está no Top 3]
  
  2. **Melhoria #Y — [nome resumido]**
     - Impacto: Alto | Esforço: Médio | Urgência: Média
     - Justificativa: [...]
  
  3. **Melhoria #Z — [nome resumido]**
     - Impacto: Médio | Esforço: Baixo | Urgência: Alta
     - Justificativa: [...]
```

4. Se houver menos de 3 melhorias no total, liste todas disponíveis

5. SEMPRE preencha esta seção — é obrigatória mesmo se houver poucas melhorias
